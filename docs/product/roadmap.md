路线图采用“完成当前门槛后再进入下一阶段”的原则。除非真实数据证明现有模块化单体成为瓶颈，否则不提前拆微服务。

## 2. 当前产品状态

已经可支持：

- 本地完整面试训练；
- Demo 模式无 Key 演示；
- 语音与文字双输入；
- 4 个技术/HR 面试轮次；
- 6 阶段配置化状态机；
- Markdown 面试记录；
- 受控只读平台控制台；
- API、AgentRun 和工具运行时展示。

当前仍不等同于公测生产系统。主要缺口不在“能否跑起来”，而在账号、数据、安全、成本和运营。

## 3. 公测前 P0 门槛

### 3.1 账号与租户

目标：

- 用户注册、登录、登出和会话管理；
- 用户与租户、角色、权限绑定；
- 管理员与普通候选人隔离；
- API Key 和服务身份管理。

验收：

- 未登录用户不能访问个人记录；
- 跨租户访问被拒绝；
- 管理员操作有审计；
- 账号删除与数据删除流程可验证。

### 3.2 数据与存储

目标：

- 从本地文件/SQLite 迁移到 PostgreSQL；
- 简历和语音使用对象存储；
- 数据库迁移、备份和恢复脚本；
- 会话、报告、导出和删除的一致性。

验收：

- 多实例部署不会相互覆盖；
- 备份可以恢复；
- 删除请求覆盖数据库、对象存储和导出文件；
- 数据保留策略可以自动执行。

### 3.3 安全与成本

目标：

- HTTPS、域名和反向代理；
- 限流、并发控制、租户配额；
- Provider Key 服务端托管；
- 输入内容安全与输出审计；
- 成本告警和上限。

验收：

- 单个租户无法耗尽全部预算；
- 超限请求有明确错误；
- Key 不出现在浏览器、日志或仓库；
- 常见注入、越权和重放请求被拒绝。

### 3.4 可观测与可靠性

目标：

- 结构化日志、指标和告警；
- 请求 Trace 与 AgentRun 关联；
- 模型/ASR/TTS 错误率和延迟看板；
- 超时、重试、熔断和降级演练。

验收：

- 能在一次请求中定位模型、工具和存储失败点；
- P95 延迟和错误率有基线；
- Provider 故障时可降级为文字或固定题目；
- 有明确值班和故障处理手册。

### 3.5 质量与内容治理

目标：

- 扩充真实匿名面试样本；
- 双人评审和评分一致性统计；
- 场景包版本、发布和回滚流程；
- 不当问题、重复问题和越界阶段自动检测；
- 用户反馈闭环。

验收：

- 新场景包必须通过配置和黄金集回归；
- 评分漂移有监控；
- 重复问题率和阶段遵守率达到门槛；
- 用户可以反馈并触发人工复核。

### 3.6 公测运营

目标：

- 隐私政策、用户协议和免责声明；
- 公测白名单或邀请码；
- 反馈渠道、问题分级和版本公告；
- 成本、容量和扩容预案。

验收：

- 小规模受邀用户可稳定完成完整流程；
- 关键故障有回滚方案；
- 用户支持问题有负责人和处理时限；
- 公测指标可持续跟踪。

## 4. 产品扩展顺序

公测前不扩大业务面，先完成技术面试纵向质量。公测后再按验证顺序扩展：

1. **场景扩展**：数据、产品、运营、校招和英文面试。
2. **训练闭环**：错题本、周期复练、专项训练计划和能力地图。
3. **内容资产**：可版本化题库、评分样例和参考答案。
4. **团队能力**：企业题库、团队看板、培训分析和教练协作。
5. **平台能力**：更完整的模型路由、成本中心、评测队列和工具生态。

## 5. 不建议提前做

- 为了看起来“更像平台”而拆微服务；
- 在无真实并发数据前引入 Kafka、Kubernetes 或复杂服务网格；
- 先做复杂计费再看用户是否愿意使用；
- 让完全自主 Agent 替代确定性面试流程；
- 用公开演示实例直接承载所有访客的真实 Key 和真实简历。

## 6. 阶段成功指标

公测准备阶段重点观察：

- 完整面试完成率；
- 报告生成成功率；
- 文字/语音输入成功率；
- 平均完成时长和放弃节点；
- 重复问题率；
- 阶段遵守率；
- 模型调用 P50/P95 延迟；
- 单轮平均模型成本；
- 用户对复盘可执行性的反馈；
- 数据删除和导出请求完成率。

这些指标稳定后，再决定是否扩大岗位范围和商业化投入。
